# Available LLM Replacement

## Result

The unavailable `Qwen2.5-7B-Instruct` generation configuration has been replaced in the isolated generation layer with the verified available instruction model **`gpt-5-mini`**. The deterministic LangGraph graph, prompt construction, BM25 retrieval, reranking status, citation formatter, and source records are unchanged.

| Item | Verified configuration |
| --- | --- |
| Previous model | `Qwen2.5-7B-Instruct` |
| Replacement model | `gpt-5-mini` |
| Selection basis | Present in the live provider catalog and completed a live provider generation call |
| Runtime | Server-side Manus Forge OpenAI-compatible Chat Completions API |
| Model selection | `RAG_GENERATION_MODEL=gpt-5-mini` |
| Authorization guard | `OPENSTAX_GENERATIVE_AI_PERMISSION_CONFIRMED=true`, based on the user's confirmation of written OpenStax authorization |
| Prompt interface | Existing system/user prompt with retrieved OpenStax context, grounding instruction, and source-label citation instruction |

## Generation-layer changes

`backend/config.py` now provides `generation_model`, configured from `RAG_GENERATION_MODEL` with a `gpt-5-mini` default. The preflight still requires the authorization flag and server-side Forge credentials, but no longer requires a Qwen-specific availability flag.

`backend/generation.py` now contains `ConfiguredLLMGenerator`, which reads the configured model rather than hard-coding Qwen. It continues to call only the server-side OpenAI-compatible endpoint, uses `max_completion_tokens` for GPT-family models, returns explicit unavailable results for provider HTTP errors, and never manufactures an answer.

`backend/graph.py` depends on the configurable generator and exposes the configured model in its health payload. `backend/schemas.py` now accepts the already-documented `generated` generation-stage status. No retrieval-related module was modified.

## Real grounded generation verification

A real request was sent through the restarted local Express-to-FastAPI proxy:

```json
{
  "question": "What are the four functions of management?",
  "top_k": 5,
  "conversation_id": "available-model-grounded-test"
}
```

The result was HTTP 200 with `answer_status: "generated"`. The response stated that the four primary functions are **planning, organizing, leading, and controlling**, and cited the retrieved labels for pages 252, 225, and 224. It retained five real OpenStax citation records and five retrieved documents. The answer was generated by the live provider, not hard-coded.

The published deployment was also verified after its rollout completed. `GET /api/health` reported `model: "gpt-5-mini"` and `generation.status: "ready"`. A subsequent production `POST /api/chat` request using the same management-functions question returned HTTP 200 with `answer_status: "generated"`, `generation.status: "generated"`, five retrieved OpenStax documents, and five preserved citation records.

The production response's `citations` array was inspected directly: it contained **five** entries, each with a `chunk_id`, `source_title: "Introduction to Business"`, `page`, `chapter`, and `official_book_url: "https://openstax.org/details/books/introduction-business"`. This independently verifies that the live generated response retained the required citation payload rather than merely returning retrieved-document page fields.

## Automated verification

The focused FastAPI real-generation contract test passed. It confirms a nonempty generated answer, generated generation stage, completed BM25 retrieval, unchanged unavailable reranking status, and provenance-preserving citations. The full project validation also passed: TypeScript compilation and 15 Vitest tests across 11 files.

## Limitations

The model runs remotely through the server-side provider rather than locally. The application still has BM25 retrieval only because the separate dense and reranking artifacts remain unavailable; this replacement does not change those truthful status fields. Provider outages return an explicit unavailable generation result. The authorization confirmation is an operational record of the user's stated written permission; the project does not store the underlying document.
